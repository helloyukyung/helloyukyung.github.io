현재 팀이 지향하고자 하는 방향을 알 수 있었던 책.

XP는 소프트웨어 개발에서 생기는 문제들을 다루기 위한 가치, 원칙, 실천 방법이다.
클린코드와 마찬가지로 테스트 코드의 중요성을 강조했다.

인상 깊었던 실천 방법으로는 '함께 앉기'와 '단일 코드 기반'이 이었다.
특히 '딘일 코드 기반'에서는

```
코드 흐름은 오직 하나뿐이어야 하며, 잠시 가지를 분기시켜 작업할 수는 있어도 분기되는 시간은 한정되어야 한다.
여러 다발의 코드 흐름은 엄청난 낭비를 낳는 근원이다. 한 결함을 고쳤을경우 나머지 코드에도 똑같이 적용이 필요하다.
```

라고 말했다.
그래서 모노래포에 관해 더욱더 도입해야겠다고 생각을 하던 찰나 감상평 글을 쓰는 시점에,
[한 블로그 글](https://xionwcfm.tistory.com/m/489)을 보게 되었는데 한편으로 "과연 모노레포가 정답일까" 라는 생각도 들게 되는 글이었다.

한 팀원이 저지른 실수는 다른 사람에게도 영향을 미쳐 팀의 시간, 에너지, 신뢰를 깎아먹는다.
변화가 뿌리내리려면 보상 체계와 조직 문화를 개인의 생산성 대신 전체적인 처리량에 맞출 필요가 있다.

신뢰는 참여자들에게 활기를 불어넣는다.
우리는 일이 순조롭게 진행될 경우 기분이 좋아진다:)

비즈니스 이유에 따라서만 설정된 마감일과 기능의 범위는 팀의 성실성을 유지하지 못한다. 개발자의 욕구 또한 정당하다.
